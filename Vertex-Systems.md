# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The Vertex Systems company website: a marketing site (`/`) for a small business-systems/automation/software-development agency, with a working CRM demo (`/systems/crm/*`) and three lightweight system-demo preview pages (`/systems/booking`, `/systems/operations`, `/systems/automation`) built in. Single Vite/React SPA on the frontend; a separate Firebase Cloud Functions backend serves the CRM only — the marketing site and preview pages are fully static.

There is no test suite in this repo.

## Commands

Run from the repo root unless noted.

```bash
npm install              # frontend deps
npm run dev               # Vite dev server
npm run build              # tsc -b && vite build — always run this (not just tsc) before calling a change done
npm run lint                # oxlint
npm run seed                  # push mock data into Firestore (requires GOOGLE_APPLICATION_CREDENTIALS)
npm run emulators               # firebase emulators:start (Auth + Firestore + Functions)
```

Cloud Functions (`functions/`) are a separate npm project:

```bash
npm --prefix functions run build     # tsc — Functions have their own tsconfig, not part of the root tsc -b graph
npx firebase deploy --only functions,hosting,firestore
```

`npx tsc -b` at the root only type-checks the frontend (`tsconfig.app.json` + `tsconfig.node.json`); it does **not** cover `functions/`. Check both independently when touching backend code.

## Architecture

### Routing (`src/App.tsx`)

Single `HashRouter` (`.../#/...`) with three route groups:
- `<MarketingLayout>` wraps `/` (a single scrolling page, `src/pages/marketing/Home.tsx`) and the three `/systems/{booking,operations,automation}` preview pages.
- `/systems/crm/login` → `Login`, unauthenticated.
- `<ProtectedRoute><Layout>` wraps everything under `/systems/crm/*` (Dashboard, Leads, Customers, Appointments, Tasks, Notes, Activity, Reports).
- A catch-all redirects unmatched paths to `/`.

**Because it's a `HashRouter`, plain `<a href="#id">` in-page anchors don't work** — the browser rewrites the fragment and the router reinterprets it as a route change. Section-scrolling on the marketing site is done via `element.scrollIntoView()` in click handlers (same page) or `navigate('/', { state: { scrollTo: id } })` read back by an effect in `Home.tsx` (cross-page). Follow this pattern for any new same-page navigation; don't reach for `href="#..."`.

### CRM data layer: Firebase-optional by design

`src/lib/firestoreCollections.ts` exports one hook per collection (`useLeads`, `useCustomers`, `useAppointments`, `useTasks`, `useNotes`, `useActivity`), all built on a generic `useLiveCollection` helper. Each hook **falls back to the static mock data in `src/data/*.ts` whenever `VITE_FIREBASE_PROJECT_ID` is unset**, and only subscribes to a live Firestore `onSnapshot` listener once a real project is configured (`isBackendConfigured` / the `firebaseConfigured` check). `src/lib/AuthContext.tsx` mirrors this: `ProtectedRoute` renders its children unguarded when Firebase isn't configured, so the CRM is always browsable with zero setup. **Any change to CRM data logic must preserve this fallback** — it's the intended "run instantly, connect a real backend later" behavior, not a stopgap to clean up. `src/lib/firebase.ts` also fills in non-empty placeholder config values when env vars are missing, because the Firebase SDK throws synchronously on `getAuth()` if `apiKey` is empty/undefined — don't remove those placeholders.

### CRM backend (`functions/`, Firebase Cloud Functions)

Three surfaces, each solving a different integration case:
- **Firestore, direct** — the CRM frontend reads/writes Firestore directly via the client SDK for everything a signed-in user does (real-time via `onSnapshot`).
- **REST API** (`functions/src/rest-api.ts`, mounted at `/api/*`) — for external tools that aren't a browser session. Every resource route is generated by the generic `crudRouter(collection)` factory in `functions/src/crud.ts`; add a new REST resource by calling that factory, not by hand-rolling routes. Auth is `x-api-key` (service-to-service) or `Authorization: Bearer <Firebase ID token>` (`functions/src/auth-middleware.ts`).
- **Webhooks** — inbound (`functions/src/webhooks.ts`, `POST /webhooks/lead-intake`, gated by a shared-secret header, for external lead capture) and outbound (`functions/src/triggers.ts`, Firestore `onDocumentCreated`/`onDocumentUpdated` triggers that POST CRM events to a Make.com webhook URL).

Secrets (`REST_API_KEY`, `INBOUND_WEBHOOK_SECRET`, `MAKE_OUTBOUND_WEBHOOK_URL`) are declared via `firebase-functions/params` `defineSecret` in `functions/src/env.ts` and read from `process.env` at runtime — set them with `firebase functions:secrets:set` (or `functions/.secret.local` for the emulator), never hardcode them.

Timestamps everywhere (CRM data and Functions writes) are plain ISO strings (`new Date().toISOString()`), not Firestore `serverTimestamp()` — this keeps writes from the REST API, the client SDK, and the seed script producing identical shapes. Keep new write paths consistent with this.

### Shared UI (`src/components/ui.tsx`)

`Card`, `Badge` (color keyed by the exact string passed as children — add new statuses to the `badgeColors` map), `StatCard`, and the `accentClasses`/`Accent` palette (`indigo`/`emerald`/`amber`/`rose`) are shared by both the marketing site and the CRM. There is no manual dark-mode toggle anywhere — theming is Tailwind's default `dark:` / `prefers-color-scheme` strategy throughout; don't introduce a toggle or a second design system for new marketing sections.

### Marketing site content (`src/data/marketing.ts`)

Homepage/preview-page copy (services, placeholder case studies, the 4 system-demo cards, process steps, team blurb) lives in one typed data file, mirroring the CRM's `src/data/*.ts` mock-data pattern — edit content there rather than inline in components. `src/components/marketing/SystemStubPage.tsx` is a generic template (title/tagline/icon/accent/features props) driving all three `/systems/{booking,operations,automation}` pages; add a new preview page by supplying content to that template, not by writing a new page from scratch.
